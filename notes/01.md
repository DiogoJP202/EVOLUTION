# Comandos
- `dotnet new sln -n TaskManager`

  - Cria uma Solution chamada `TaskManager`.
  - Uma solution serve para agrupar e organizar vários projetos relacionados, por exemplo:

    TaskManager.Api
    TaskManager.Application
    TaskManager.Domain
    TaskManager.Infrastructure
    TaskManager.Tests

  - A solution não é a aplicação em si; ela funciona como um agrupador/orquestrador dos projetos.

  - A partir do .NET 10, o formato padrão criado é `.slnx`.
    Em versões anteriores, o padrão era `.sln`.

  - Se quiser forçar o formato antigo:
    `dotnet new sln -n TaskManager --format sln`

- `dotnet new webapi -n TaskManager.Api`

  - Cria um projeto ASP.NET Core Web API chamado `TaskManager.Api`.

  - Cria arquivos como:
    - `Program.cs`
    - `TaskManager.Api.csproj`
    - `appsettings.json`
    - `appsettings.Development.json`
    - `Properties/launchSettings.json`

  - Por padrão, nos SDKs atuais, o template usa Minimal APIs.

  - Para criar usando Controllers:
    `dotnet new webapi -n TaskManager.Api --use-controllers`

  - O template também pode incluir suporte a OpenAPI e um endpoint de exemplo, como `/weatherforecast`.

- `dotnet sln add TaskManager.Api/TaskManager.Api.csproj`

  - Adiciona o projeto `TaskManager.Api` à solution localizada no diretório atual.

  - Isso não copia nem move o projeto. Apenas registra uma referência ao projeto dentro da solution.

  - Depois disso, ferramentas como Visual Studio e `dotnet build` podem tratar a solution e seus projetos como um conjunto.

## Comandos Utéis:

- `dotnet --version`
  Mostra a versão do SDK .NET que está sendo utilizada.

- `dotnet new list`
  Lista os templates de projeto disponíveis no SDK e os templates instalados.

- `dotnet build`
  Restaura dependências se necessário e compila o projeto ou solution.

- `dotnet run`
  Compila o projeto, se necessário, e executa a aplicação. Também pode utilizar os profiles definidos no `launchSettings.json`.

- `dotnet clean`
  Remove os artefatos gerados por builds anteriores, incluindo arquivos intermediários em `obj/` e finais em `bin/`.

- `dotnet test`
  Compila a solution/projeto de testes e executa os testes.

- `dotnet add package NomeDoPacote`
  Adiciona uma referência a um pacote NuGet no projeto e executa o restore das dependências.

# Estrutura criada

- `bin/`: Pasta gerada automaticamente durante a compilação. Guarda os artefatos finais da build, como `.dll`, `.exe`, `.pdb`, `.deps.json`, `.runtimeconfig.json` e outros arquivos necessários para executar a aplicação. Normalmente possui subpastas como `Debug/` e `Release/`, além da versão do framework, como `net8.0/`. Não deve ser editada manualmente nem versionada no Git.

- `obj/`: Pasta gerada automaticamente pelo MSBuild durante o processo de compilação. Guarda artefatos intermediários da build, arquivos gerados, caches, metadados e informações usadas pelo compilador e pelo NuGet, como `project.assets.json`. Serve como uma área de trabalho temporária para produzir o conteúdo final de `bin/`. Não deve ser editada manualmente nem versionada no Git.

> obj = oficina. bin = produto pronto da compilação.

- `Properties/launchSettings.json`: é um arquivo de configuração de inicialização usado pelo tooling para definir diferentes perfis de execução local, incluindo como o projeto será iniciado, URLs/portas, variáveis de ambiente, argumentos, abertura do navegador, flags e outros comportamentos de launch. Exemplo:
    ```json
    {
        "profiles": {
            "Local": { // Nome do perfil
                "commandName": "Project",
                "dotnetRunMessages": true,
                "launchBrowser": true,
                "launchUrl": "swagger",
                "applicationUrl": "https://localhost:7043;http://localhost:5043", // Url da onde a aplicação estará rodando.
                "environmentVariables": { // Variáveis de ambientes que podem ser usadas na execução.
                    "ASPNETCORE_ENVIRONMENT": "Development",
                    "FeatureFlags__UseMockPayment": "true"
                }
            }
        }
    }
    ```

    - `profile`
    São vários perfils que podem ser executados para ter condições de execuções diferentes.

    - `commandName`
    É um commando que modifica o comportamento de execução da aplicação, alguns comuns são: `Project`, `Executable` e `IISExpress`.

    - `applicationUrl`
    Descide a url onde a aplicação vai rodar.

    - `environmentVariables`
    Aqui são váriaveis que podem ser usadas dentro da aplicação, podem ser poderosas. Alguns frameworks podem ter suporte para elas, podendo criar alguns processos mais interessantes.
    
    - `launchBrowser`
    É uma configuração que avisa ao tooling que se possível abra o navegador padrão com a aplicação depois que ela estiver rodando.
    
    - `dotnetRunMessage`
    Configura se as mensagens ao executar a aplicação com `dotnet run` devem aparecer, dependendo do tooling, essas mensagens podem ser expostas de formas diferentes.

    - `commandLineArgs`
    Isso permite usar argumentos na execução da aplicação e pode ser muito interessantes em alguns casos, como perfils de execuções de seeds no banco.

- `appsettings.json`
É uma das fontes do sistema de configuração do ASP.NET Core. Quando `WebApplication.CreateBuilder(args)` é executado, o framework configura diversos Configuration Providers, responsáveis por buscar valores de diferentes fontes, como JSON, variáveis de ambiente e argumentos de linha de comando. Essas fontes são expostas de forma unificada através de `builder.Configuration`, permitindo que a aplicação consulte uma configuração sem precisar conhecer sua origem. Arquivos específicos de ambiente, como `appsettings.Development.json`, podem sobrescrever chaves do `appsettings.json` quando aquele ambiente estiver ativo.

## Program.cs

Esse arquivo é o ponto de entrada da aplicação. Quando se roda `dotnet run` o processo eventualmente começa pelo código do `Program.cs`, ele virou o lugar onde são definidos os serviços necessários da aplicação e o pipeline de processamento das requisições HTTP.

## WebApplication.CreateBuilder(args)

Aqui ele cria uma instância de `WebApplicationBuilder` já com vários padrões do ASP.NET Core configurados. O objeto criado leva todas as coisas necessárias para se criar a aplicação, ele carrega coisas como: `builder.services`, `builder.configuration`, `builder.logging`, `builder.environment`, `builder.webhost` e `builder.host`.

os args vem dos argumentos da linha de comando. `dotnet run --MinhaConfig=123`

## `builder.Services`
Isso representa a coleção de serviços que serão registrados no conteiner de Dependency Injection para serem servidos a aplicação. Como por exemplo: `builder.Services.AddControllers();`, `builder.Services.AddOpenApi();`, `builder.Services.AddDbContext<AppDbContext>();`, `builder.Services.AddScoped<IUserRepository, UserRepository>();` e `builder.Services.AddScoped<UserService>();`.

## `Build()`
Depois da fase de configuração, a aplicação de fato é construida aqui, é onde é gerado a instância de WebApplicaation que representa a aplicação ASP.NET Core que poderá configurar o pipeline HTTP, endpoints e depois ser executada.

> Builder -> Configura como a aplicação será construída.
> app -> Configura como a aplicação construída se comporta.

## Pipeline HTTP

Aqui é onde é configurado como as requisições HTTP serão processadas. Ex: `app.UseHttpsRedirection();`, `app.UseAuthentication();`, `app.UseAuthorization();` e `app.MapControllers();`. Quando alguém fizer uma requisição `GET /users/10` ela pode passar por `Request -> HTTPS Redirection -> Authentication -> Authorization -> Endpoint -> Controller -> Response` Esse é o HTTP Request Pipeline.

> Pipeline é uma sequência de componentes de middleware responsáveis por processar requisições.

## Use... e Map...

`Use...` normalmente configura comportamento do pipeline/middleware como `app.UseHttpsRedirection();`
Quando se é `Map...` normalmente está mapeando endpoints como `app.MapGet(...)` ou `app.MapControllers();`.

O trecho `builder.Services.AddOpenApi();` registra os serviços necessários para gerar a documentação.
O trecho:
```c#
if (app.Environment.IsDevelopment()){
    app.MapOpenApi();
}
```
Criar o endpoint HTTP que expõe essa documentação, como `/openapi/v1.json.`
> O endpoint `/weatherforecast` é só um exemplo do template e não usa Controller. Ele usa Minimal API, que é quando você define uma rota direto no `Program.cs`.

> Mapear um endpoint é dizer: "Quando alguém fizer uma requisição para essa rota, execute isso aqui!".

- `app.Run();`: Essa linha faz a aplicação começar a escutar requisições HTTP. Antes dela, você está configurando a aplicação. Depois dela, a API entra em execução.

### Fluxo mental do Program.cs:
CreateBuilder
-> registra serviços
-> Build
-> configura pipeline/endpoints
-> Run

Existem duas formas de criar Endpoints no ASP.NET Core:
`app.MapGet("/rota", () => "resultado");` -> Isso é Minimal Api.

E existe o modelo com Controllers:
```c#
[ApiController]
[Route("api/task")]
public class TasksController : ControllerBase{

}
```
Isso é Controller-Base Api. 

# Controllers

A Controller é uma classe do Asp.Net Core que pode receber requisições HTTP e retornar respostas HTTP. Ela Herda de `ControllerBase`
```c#
[ApiController]
[Route("api/tasks")]
public class TaskController : ControllerBase
{
    [HttpGet]
    public IActionResult Get()
    {
        return Ok("Olá!");
    }
}
```
Ela faz as seguintes perguntas quando chega uma requisição:

- Existe alguma classe que atende essa rota?
- Existe algum método GET nela?
- Quais parâmetros ela recebe?
- Como executar esse método?

Ele não descobre isso automáticamente, ai que entra o `MapControllers();`'
Ao executar `var builder = WebApplication.CreateBuilder(args);`, aqui ainda está construindo a aplicação. Depois ao executar `builder.Services.AddControllers();` é registrado todos os serviços necessários para trabalhar com Controllers. Isso inclui: Descoberta de Controllers, Model Binding, Validação, Serialização Json, filtros,  IActionResult e Atributos com [ApiController].

> Registrar não significa usar necessáriamente.

## O Build()

Depois disso, vem o `var app = builder.Build();`. Aqui o ASP.NET pega tudo que foi registrado e constroi a aplicação de verdade. Até esse momento, não temos nenhuma rota.

## MapControllers()

O comando `app.MapControllers();` faz com que execute algo como: Percorra todas as classes do projeto > Essa classe possui [ApiController] ? > Ela Possui [Route] ? > Quais métodos possuem ? > Registre todas essas rotas.

Depois do MapControllers(), o ASP.NET meio que monta uma tabela interna parecida com:

| Método | URL | Método C# |
|---------|-----|-----------|
| GET | /api/tasks | TasksController.Get |
| POST | /api/tasks | TasksController.Create |
| GET | /api/users | UsersController.List |

> Essa tabela é chamada de Routing Table (Tabela de rotas).

## Explicando

- `[ApiController]`: marca a classe como uma Controller de API. Também ativa comportamentos automáticos, como validação de entrada.
- `[Route("api/exemple")]`: Define a rota base do Controller.
- `[HttpGet]`: Diz que esse método responde a requisições GET/
- `IActionResult`: Representa uma resposta HTTP. Pode ser `200 OK`, `404 Not Found`, `400 Bad Request` e por aí vai.
- `Guid`: Globally Unique Identifier. É um identificador enorma, dificilmente sendo valores únicos por sua natureza.

## O que é Routing?
Routing, ou roteamento, é o processo que o ASP.NET Core utiliza para analisar uma requisição e descobrir qual endpoint deve atendê-la, considerando fatores como a URL e o método HTTP utilizado.

## Model Binding
Quando uma requisição passa um atributo exigido pelo endpoint, o asp.net por baixo dos panos, identifica aquele atributo atravez do seu nome e faz a conversão do tipo de dados automaticamente. Ele sabe pegar dados de vários lugares, não apenas com rotas, mas de query strings, body de requisições e headers.

## Diferença entre Routing e Model Binding:
Routing é usado para identificar qual método uma requisição deve executar, enquanto o Model Binding fica responsável por trazer os dados no formato correto.

## Action
Em ASP.NET costuma ser o método público dentro de uma controller que responda uma requisição HTTP.

## CreatedAtAction
É uma função com retorno IActionResult, é usado para retorno POST quando algo foi criado e precisamos passar a url para acessar ele.

## FromBody
Quando existe um objeto complexo no parametro, o ASP.NET automaticamente supoe que ele vem do body.
`public IActionResult Put(int id, UpdateTaskItemRequest request)` -> Aqui ele assume que request é o body.
Mas também podemos deixar explícito: `[FromBody] UpdateTaskItemRequest request`

## NoContent()
Retorna: `HTTP 204 No Content` -> Significa que a operação deu certo, mas não estou enviando corpo na resposta.

# Injeção de Dependências

Ao inves de deixar que as controllers chamem as services, elas pedem a as services diretamente para a program.cs.
Precisamos registrar as services na program.cs: `builder.Services.AddSingleton<TaskItemService>();`

# Singleton
Uma instância para a aplicação inteira.
> Singleton diz que a service usada será instânciada apenas uma vez durante toda a vida da aplicação.

# Scoped
Uma instância por requisição HTTP. Dentro da mesma request, todo mundo usa a mesma instância.

# Transient
Uma nova instância toda vez que alguém pedir.

# DI
Dependency Injection é quando uma classe não fica responsável por criar suas próprias dependências. Em vez disso, ela recebe elas de fora, normalmente pelo construtor e o conteiner de DI fica responsável por criar e fornecer essas instâncias.

# Container de DI
Ele funciona como um gerenciador de instâncias usandas na aplicação. Fica responsável por registrar, criar e fornecer as dependências para as classes da aplicação. Além disso, ele também é responsável por controlar o tempo de vida dessas dependências.

# Repository
É uma camada que abstrai o acesso a dados. Ela que se comunica com o banco e traz os dados para quem solicita.

> Ao criar DI da service na controller, também é necessário ter a DI de Repository na service também, porque o Conteiner precisa fechar essa cadeia. Caso isso não houver a DI do Repository na Service o código até compila, mas ocorre um erro em runtime ao tentar resolver a dependência.

# Interface

Uma interface é como se fosse um contrato que diz que quem implementar ele, precisa ter os métodos que ele requere, mas não diz como implementar eles.

Exemplo:

```c#
public interface ITaskItemRepository
{
    List<TaskItem> GetAll();
    TaskItem? GetById(int id);
    void Add(TaskItem task);
    void Remove(TaskItem task);
    int GetNextId();
}
```

Depois a classe implementa:
```c#
public class TaskItemRepository : ITaskItemRepository {}
```

O ganho é que a Service passa a depender do contrato:
```c#
private readonly ITaskItemRepository _taskItemRepository;
```

E não da implementação completa:
```c#
private readonly TaskItemRepository _taskItemRepository;
```

No `Program.cs`, registramos:
`builder.Services.AddSingleton<ITaskItemRepository, TaskItemRepository>();`

Isso significa que se alguém pedir ITaskItemRepository, ele entregaria TaskItemRepository. Isso seria útil porque para trocar de repositório, precisariamos mexer apenas nessa linha.

o Dependency Inversion Principle, o D do SOLID: a Service não depende diretamente de um detalhe concreto, ela depende de uma abstração.

# Fake repository

Fake repository e uma implementacao simples criada para teste. Ela implementa a mesma interface da repository real, mas usa dados controlados pelo teste.

Isso funciona porque `TaskItemService` depende de `ITaskItemRepository`, nao de `TaskItemRepository`.

# Isolamento entre testes

Cada teste deve montar seu proprio cenario. Se uma fake usa estado `static`, um teste pode alterar dados que outro teste vai enxergar depois.

Por isso, em fake de teste, evitamos `static` e preferimos receber os dados pelo construtor:

```csharp
var repository = new FakeTaskItemRepository(tasks);
var service = new TaskItemService(repository);
```

# Teste Unitários 
Um teste unitário testa uma unidade pequena de código isolada, normalmente um método ou uma classe, sem depender de banco, http, arquivo, rede, etc.

# xUnit
É um framework de testes para .NET, esse framework de testes que sabe:
- Encontrar métodos marcados como teste;
- Executar esses métodos;
- Verificar se passaram ou falharam;
- Mostrar um relatório no terminal;

No xUnit, um teste simples é marcado com `[Fact]`:

O `dotnet test` procura métodos com `[Fact]`, executa cada um e mostra se deu certo.

## Como é possível testar sem rodar a API?
Isso é possível porque nem toda parte da aplicação precissa passar por HTTP. Quando rodamos a API com `dotnet run` ela faz o seguinte: 
`Kestrel -> Middlewares -> Routing -> Controller -> Service -> Repository`

Um Teste Unitário da Service chama a classe diretamente:

```c#
var repository =  new FakeTaskItemRepository();
var service = new TaskItemService(repository);

ServiceResult<TaskItem> result = service.Complete(1);
```

## AAA
É um padrão mental para organizar testes:
- Arrange: preparar o cenário.
- Act: executar a ação.
- Assert: verificar o resultado.

Exemplo:

```c#
[Fact]
public void Sum_ShouldReturnTotal()
{
    // Arrange
    int a = 2;
    int b = 3;

    // Act
    int result = a + b;

    // Assert
    Assert.Equal(5, result);
}
```

> [Fact] vem do xUnit e significa: “isso é um teste”.

## Nome de teste

É importante ter um bom nome para os teste, o mais descritivo possível. Um nome bom costuma dizer Metodo_Cenario_ResultadoEsperado, algo como: `Complete_WhenTaskIsCanceled_ShouldReturnConflict`

## Estado compartilhado entre testes

O estado é qualquer dado que fica guardado em algum lugar. Quando usamos `static` esse estado pertence a classe, não a instância. Dessa forma, todas as intâncias compartilhariam esse mesmo dado.

Exemplo:
```c#
public class FakeRepository
{
    private static List<String> _items = [];
}
```

Se o Teste A faz: `repository.Add("A");`, o Teste B pode começar com "A" já dentro da lista mesmo sem ter criado. isso deixa os testes imprevisíveis, porque um teste passa ou falha dependendo da ordem em que rodou. Em testes unitários, queremos **Isolamento**: *Cada teste deve preparar seu próprio cenário e não depender do que outro teste fez*. 
> Um bom uso, seria deixar uma lista sem `static` começando vazia, depois quando for realizar o teste, ele mesmo preenche ela.

## Helper de teste

Um helper de teste e um metodo auxiliar criado para remover repeticao de setup sem esconder o comportamento principal do teste.

Exemplo usado em `TaskItemServiceTests`:

```csharp
private static TaskItemService CreateServiceWithTasks(List<TaskItem> tasks)
{
    var repository = new FakeTaskItemRepository(tasks);
    return new TaskItemService(repository);
}
```

Ele pode ser `private` porque so precisa ser usado dentro da classe de teste.
Ele pode ser `static` porque nao depende de nenhum estado da instancia da classe de teste; ele usa apenas os parametros recebidos e cria objetos novos.

## Assert.NotNull vs Assert.Equal

Ao testar que uma tarefa concluida nao pode ser cancelada, verificar apenas isto:

```csharp
Assert.NotNull(task.CompletedAt);
```

prova que `CompletedAt` continua preenchido, mas nao prova que o valor original foi preservado.

Um teste mais forte guarda o valor antes e compara exatamente:

```csharp
DateTime completedAt = DateTime.UtcNow;

// ...

Assert.Equal(completedAt, task.CompletedAt);
```

Assim o teste falha se a regra alterar indevidamente a data de conclusao.

## Testes de integracao da API

Teste unitario da Service chama diretamente um metodo C#, por exemplo:

```csharp
service.Create(request);
```

Teste de integracao da API chama a aplicacao por HTTP, por exemplo:

```csharp
client.GetAsync("/api/tasks");
```

Ele valida se as pecas estao conectadas:

- rota;
- verbo HTTP;
- pipeline da aplicacao;
- injecao de dependencia;
- Controller;
- Service;
- Repository;
- status HTTP;
- corpo da resposta.

Para isso, foi adicionado o pacote:

```powershell
dotnet add TaskManager.Api.Tests package Microsoft.AspNetCore.Mvc.Testing
```

O `WebApplicationFactory<Program>` cria uma aplicacao ASP.NET Core em memoria para os testes. Ela nao sobe a API em `localhost`, mas permite criar um `HttpClient` para chamar as rotas.

Como o `Program.cs` usa top-level statements, foi adicionado ao final do arquivo:

```csharp
public partial class Program { }
```

Isso permite que o projeto de testes enxergue o ponto de entrada da API.

Primeiro teste de integracao criado:

```csharp
[Fact]
public async Task Get_WhenCalled_ShouldReturnOk()
{
    await using var factory = new WebApplicationFactory<Program>();
    HttpClient client = factory.CreateClient();

    var response = await client.GetAsync("/api/tasks");

    Assert.Equal(HttpStatusCode.OK, response.StatusCode);
}
```

Esse teste precisa ser `async Task` porque `GetAsync` e uma operacao assincrona e precisa ser aguardada com `await`.

### Cuidado com helper descartando a factory

Este helper nao deve ser usado assim:

```csharp
private static async Task<HttpClient> CreateClient()
{
    await using var factory = new WebApplicationFactory<Program>();
    return factory.CreateClient();
}
```

O problema e que `await using` descarta a `factory` ao sair do metodo. O `HttpClient` voltaria para o teste, mas a aplicacao em memoria criada pela factory ja teria sido encerrada.

Proximo teste sugerido:

```csharp
GetById_WhenTaskExists_ShouldReturnOk
```

Ele deve chamar `GET /api/tasks/1`, validar `200 OK` e ler o JSON com:

```csharp
TaskItem? task = await response.Content.ReadFromJsonAsync<TaskItem>();
```

É uma mudança que acontece depois que um método é chamado, tirando o retorno.

# Testes de Integração de API
Esses tipos de testes chamam a aplicação de fora e testam o fluxo completo dela, a diferença dos testes de service é que ele consegue testar controllers e respostas http.

## WebApplicationFactory
`WebApplicationFactory` é uma classe de teste do ASP.NET que cria uma versão da aplicação em memória, só para testes. Ela não sobe um servidor localhost, porém permite usar HttpClient para chamar rotas como se fosse HTTP de verdade.

Precisamos usar o pacote no projeto de teste: `dotnet add TaskManager.Api.Tests package Microsoft.AspNetCore.Mvc.Testing`.

Normalmente se cria uma classe teste que herda de `WebApplicationFactory<Program>`. 

> Para o projeto enxegar o Program.cs é necessário adicionar ao final dele: `public partial class Program { }`. Isso é comum em projetos ASP.NET Core modernos, porque o Program.cs usa top-level statements.
> Tradução simples:
> - top-level statements: quando o código fica solto no arquivo, sem class Program explícita.
> - partial class: permite declarar uma parte da classe Program em outro ponto/arquivo.
> - nesse caso, criamos uma “alça” para o teste conseguir referenciar a aplicação.

### Conceitos

- `HttpClient`: Objeto usado para enviar requisições HTTP em C#.
- `GetAsync`: Método assíncrono que envia uma requisição GET.
- `async Task`: Assinatura usada em testes que precisam esperar operações assíncronas.
- `HttpStatusCode.OK` enum do .Net que representa status HTTP 200.

Precisa usar:
```c#
using System.Net;
using Microsoft.AspNetCore.Mvc.Testing;
```

Estrutura usada normalmente:

```c#
public class TasksControllerIntegrationTests
{
    [Fact]
    public async Task Get_WhenCalled_ShouldReturnOk()
    {
        // Arrange
        await using var factory = new WebApplicationFactory<Program>();
        HttpClient client = factory.CreateClient();

        // Act
        var response = await client.GetAsync("/api/tasks");

        // Assert
        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
    }
}
```

> O `WebApplicationFactory<Program>` cria uma aplicação ASP.NET Core de teste em memória, usando o Program.cs real como ponto de entrada. Então ele monta pipeline, DI, controllers, services e repositories.
